# สรุปโครงสร้างโปรเจคและเหตุผลในการแบ่งโฟลเดอร์ (Layered Architecture)

โปรเจคนี้ถูกออกแบบตามสถาปัตยกรรม **Layered Architecture** ซึ่งเป็นการแบ่งซอร์สโค้ดออกเป็นชั้นๆ (Layers) โดยมีกฎเหล็กคือ "แต่ละชั้นจะมีหน้าที่เฉพาะของตัวเอง และห้ามเรียกข้ามชั้นกระโดดไปมา" (เช่น Controller ห้ามเรียกใช้ Repository โดยตรง ต้องผ่าน Service เสมอ)

การแบ่งโฟลเดอร์ใน `src/main/java/com/eternalclash2/` มีดังนี้:

## 1. 📁 `controller/` (Presentation Layer)
- **คืออะไร:** โฟลเดอร์สำหรับรับ Request จากผู้ใช้งาน (เช่น Frontend, Postman) และส่ง Response กลับไป (REST API)
- **ไฟล์สำคัญในชั้นนี้:**
  - `GameController.java` : จัดการ API เกี่ยวกับการสร้างห้องและเข้าร่วมห้องเกม (เช่น `POST /api/games`)
  - `TurnController.java` : รับ Action ประจำเทิร์นของผู้เล่น (ผลิตเสบียง, ส่งทหาร)
  - `GameEndpointController.java` : หน้าที่คืนค่าไฟล์หน้าเว็บ HTML ตั้งต้นให้ผู้เล่น
- **ทำไมต้องแยก:** เพื่อให้คลาสนี้ทำหน้าที่แค่ "รับ-ส่งข้อมูลและตรวจสอบสิทธิ์" เท่านั้น คลาสนี้ไม่ควรมีลอจิกคิดเลขหรือเซฟฐานข้อมูล หน้าที่ของมันคือรับคำสั่งมาแล้วโยนต่อให้ Service ทำงาน

## 2. 📁 `service/` (Business Logic Layer)
- **คืออะไร:** หัวใจหลักของแอปพลิเคชัน เป็นที่เก็บลอจิกการคำนวณ กฎเกณฑ์ของเกม (Business Rules) และควบคุม Transaction
- **ไฟล์สำคัญในชั้นนี้:**
  - `TurnService.java` : คลาสบอสใหญ่คอยประสานงานระบบเมื่อปิดเทิร์น (เดินทัพ, หักเสบียง, สุ่มอีเวนต์)
  - `CityService.java` : รับผิดชอบลอจิกเกี่ยวกับเมืองโดยเฉพาะ เช่น เมืองไหนติดกัน, ทหารจะอดตายไหม
  - `BattleService.java` : คำนวณความเสียหายเมื่อเกิดการต่อสู้ 
  - `GameEventService.java` : จัดการสุ่มภัยพิบัติในเกม
  - `GameClock.java` : (Utility/Strategy) สำหรับคำนวณว่าเทิร์นนี้คือฤดูอะไร
- **ทำไมต้องแยก:** เพื่อรวมลอจิกซับซ้อนไว้ที่เดียว หากวันหน้าต้องการเปลี่ยน UI โค้ดส่วน Service นี้จะนำไปใช้ต่อได้ทันทีโดยไม่ต้องแก้

## 3. 📁 `repository/` (Data Access Layer)
- **คืออะไร:** โฟลเดอร์สำหรับติดต่อกับฐานข้อมูล (Database) โดยตรง มักจะเป็น Interface ที่สืบทอดมาจาก `JpaRepository`
- **ไฟล์สำคัญในชั้นนี้:**
  - `GameRepository.java` : บันทึกสถานะเกม ค้นหาเกมด้วยรหัสโค้ด 6 หลัก
  - `CityRepository.java` : ดึงข้อมูลเมืองทั้งหมดมาอัปเดตทรัพยากร
  - `GameEventRepository.java` : บันทึกประวัติภัยพิบัติลงฐานข้อมูล
- **ทำไมต้องแยก:** เพื่อซ่อนความซับซ้อนของคำสั่ง SQL (Repository Pattern) ทำให้ Service แค่สั่ง `save()` หรือ `findAll()` ก็พอ ไม่ต้องปวดหัวกับเรื่องฐานข้อมูลเชิงลึก

## 4. 📁 `domain/` (Domain Model Layer)
แบ่งย่อยเป็น 2 โฟลเดอร์:
- **`entity/`**: คลาสที่สะท้อนถึงตารางในฐานข้อมูล (เชื่อมกับ JPA ด้วย `@Entity`)
  - `Game.java`, `Player.java`, `City.java`, `Army.java`: คลาสหลักที่ใช้เก็บข้อมูลจริง
  - `PlayerActionCommand.java`: (Interface) รองรับการเขียนโค้ดแบบ Command Pattern
- **`enums/`**: ค่าคงที่ต่างๆ ที่ใช้ควบคุมลอจิกของระบบ
  - `GameStatus.java` : สถานะ (WAITING, IN_PROGRESS, FINISHED)
  - `EventType.java` : ชนิดภัยพิบัติ (FLOOD, STARVATION)
- **ทำไมต้องแยก:** เพื่อให้เป็น "ศัพท์กลาง" ของโปรเจค ที่ทุก Layer สามารถเรียกใช้ร่วมกันได้ เป็นโมเดลหลักที่ใช้อธิบายระบบเกม

## 5. 📁 `dto/` (Data Transfer Object)
- **คืออะไร:** คลาสที่ใช้บรรจุข้อมูลสำหรับแพ็กใส่กล่อง "ส่งออก" หรือ "รับเข้า" จาก API (API Contract)
- **ไฟล์สำคัญในชั้นนี้:**
  - `GameSnapshotDto.java` : แพ็กข้อมูลทั้งเกม (เมือง, ทหาร, กษัตริย์) รวมเป็นก้อนเดียวส่งให้หน้าจอ React ทีเดียวจบ (Facade Pattern)
  - `ActionRequestDto.java` : ข้อมูลที่ส่งมาจากหน้าเว็บว่าผู้เล่นจะทำแอ็กชันอะไร
- **ทำไมต้องแยก:** เพื่อป้องกันการส่ง `Entity` ก้อนใหญ่กลับไปตรงๆ ซึ่งอาจทำให้มีปัญหา Infinite Recursion (วงจรข้อมูลซ้อนทับกันไม่จบ) และช่วยปกปิดข้อมูลที่ไม่จำเป็นไม่ให้หลุดรอดไปถึง Client

## 6. 📁 `exception/`
- **คืออะไร:** เก็บ Custom Exception ที่เราสร้างขึ้นเอง และที่ดักจับ Error ส่วนกลาง
- **ไฟล์สำคัญในชั้นนี้:**
  - `BusinessLogicException.java` : Error เฉพาะของเกม เช่น "ทหารไม่พอส่งไปโจมตี" หรือ "เทิร์นยังไม่จบ"
  - `GlobalExceptionHandler.java` : (@RestControllerAdvice) ตัวดักจับเวลาระบบพัง ให้พ่น Error คืนกลับไปหา Client ในรูปแบบ JSON สวยๆ เสมอ
- **ทำไมต้องแยก:** เพื่อรวมศูนย์การจัดการ Error ไว้ที่เดียวให้เป็นระเบียบ

## 7. 📁 `strategy/` (เฉพาะกิจสำหรับพฤติกรรม)
- **คืออะไร:** พื้นที่เก็บคลาสที่ใช้จัดการลอจิกที่มีหลายรูปแบบ (Strategy Pattern)
- **ไฟล์สำคัญในชั้นนี้:**
  - `CombatStrategy.java` (Interface)
  - `KongmingCombatStrategy.java` : ลอจิกการต่อสู้พิเศษของตัวละครที่ชื่อ ขงเบ้ง
- **ทำไมต้องแยก:** หากตัวละครมีการโจมตีแตกต่างกัน 10 แบบ เราจะไม่เขียน if-else 10 ชั้นซ้อนกัน แต่จะแยกแต่ละวิธีออกเป็นคลาสย่อยๆ (Open/Closed Principle)

## 8. 📁 `state/` (สถานะของเกมและการประยุกต์ใช้ State Pattern)
- **คืออะไร:** โฟลเดอร์ที่ใช้คุม "พฤติกรรมที่เปลี่ยนไปตามสถานะ" (State-dependent behavior) โดยใช้ **State Design Pattern (GoF)** ซึ่งเป็นหนึ่งใน Behavioral Pattern ที่สำคัญ
- **ปัญหาที่ Pattern นี้เข้ามาแก้:** ในเกมแบบ Turn-based สถานะของเกม (เช่น รอคนเข้า, กำลังเล่น, จบเกมแล้ว) จะมีผลต่อการทำงานของระบบอย่างมาก ถ้าเราเขียนแบบปกติใน Service ลอจิกจะเต็มไปด้วย `if (status == WAITING) { ยอมให้ Join } else if (status == PLAYING) { ห้าม Join แต่ออกคำสั่งได้ }` ซึ่งเมื่อเกมขยายสเกลขึ้น โค้ดส่วนนี้จะยาวเป็นพันบรรทัดและแก้บั๊กยากมาก (Spaghetti Code)
- **ไฟล์สำคัญและกลไกการทำงาน:**
  - `GameStatePhase.java` : (Interface) ทำหน้าที่เป็นข้อตกลงว่า ทุกๆ สถานะในเกมนี้ "ต้อง" สามารถรับมือกับการกด Join, กด Start, กดออกคำสั่ง ได้ 
  - `GameStateContext.java` : ทำหน้าที่เป็น "กล่องเก็บสถานะปัจจุบัน" เมื่อ `GameService` ต้องการทำอะไร จะไม่ทำเอง แต่จะสั่งผ่าน Context แล้ว Context จะโยนคำสั่งให้ State ปัจจุบันเป็นคนตัดสินใจ
  - `WaitingPhaseState.java` : คลาสนี้จะรับผิดชอบเฉพาะตอน "รอคนเต็มห้อง" เท่านั้น เช่น ถ้ามีคำสั่ง Join เข้ามา คลาสนี้จะยอมให้เข้า แต่ถ้ามีคำสั่ง "โจมตี" เข้ามา คลาสนี้จะพ่น Error กลับไปว่า "เกมยังไม่เริ่ม โจมตีไม่ได้!"
  - `PlayPhaseState.java` : ตรงข้ามกับด้านบน คลาสนี้รับผิดชอบตอน "เริ่มเกมแล้ว" ถ้ามีคนขอ Join คลาสนี้จะปฏิเสธทันที แต่จะยอมรับคำสั่ง "โจมตี" หรือ "เกณฑ์ทหาร" แทน
  - `FinishedPhaseState.java` : รับผิดชอบตอนเกมจบแล้ว ทุกคำสั่งที่เข้ามาจะถูกปฏิเสธทั้งหมด (เกมจบแล้วทำอะไรไม่ได้)
- **ทำไมต้องแยก (ประยุกต์ใช้ SOLID):** 
  - **Single Responsibility Principle (SRP):** แต่ละคลาสรับผิดชอบแค่สถานะของตัวเองเท่านั้น
  - **Open/Closed Principle (OCP):** สมมติในอนาคต อาจารย์สั่งให้เพิ่มระบบ "หยุดเกมชั่วคราว (Pause)" เราก็ไม่ต้องไปนั่งไล่แก้ `if-else` เดิมให้พัง แค่สร้างคลาสใหม่ `PausePhaseState.java` มาเสียบเข้าไป ระบบก็ทำงานต่อได้เลย นี่คือความเจ๋งของการจัดโฟลเดอร์แบบ State Pattern ครับ

## 9. 📁 `command/` (ชุดคำสั่งของผู้เล่น)
- **คืออะไร:** โฟลเดอร์ที่รวบรวม "คำสั่ง" ทุกชนิดที่ผู้เล่นสามารถกดกระทำได้ในเกม (Action) ออกแบบโดยใช้ **Command Pattern** (มักจะใช้คู่กับ Factory Pattern)
- **ไฟล์สำคัญในชั้นนี้:**
  - `PlayerActionCommand.java` : (Interface) หน้าต่างหลักที่กำหนดว่าทุกๆ คำสั่งต้องมีฟังก์ชัน `execute()` สำหรับรันลอจิก
  - `ProduceFoodCommand.java` : เก็บโค้ดสำหรับคำสั่ง "ผลิตเสบียง"
  - `RecruitSoldiersCommand.java` : เก็บโค้ดสำหรับคำสั่ง "เกณฑ์ทหาร"
  - `SendArmyCommand.java` : เก็บโค้ดที่ซับซ้อนที่สุด คือการ "ส่งกองทัพข้ามเมือง" และหักเสบียงตามระยะทาง
  - `CommandFactory.java` : "โรงงาน" ที่คอยอ่านข้อมูล Request แล้วแจกแจงว่าจะต้องปั้น Command ตัวไหนส่งให้ Service ไปรัน
- **ทำไมต้องแยก:** ในเกมแนว Turn-based ผู้เล่น 1 คนสามารถทำอะไรได้หลายอย่างมาก ถ้าเราเอาลอจิกของการ "เกณฑ์ทหาร", "ทำนา", "เดินทัพ" ไปยัดรวมกันใน `TurnService` ไฟล์เดียว โค้ดจะบวมเป็นหลายพันบรรทัด การแยกคำสั่งออกมาเป็นแต่ละคลาส (Command Pattern) จะช่วยให้เราสามารถเพิ่ม Action ใหม่ๆ (เช่น ในอนาคตมีคำสั่ง "ซุ่มโจมตี") ได้ง่ายๆ แค่สร้างคลาสใหม่ โดยไม่กระทบโค้ดเดิมครับ

## 10. 📁 `config/` (ตั้งค่าระบบระดับโครงสร้าง)
- **คืออะไร:** โฟลเดอร์สำหรับเก็บไฟล์ตั้งค่า (Configuration) ของ Spring Boot ที่มีผลกระทบกับทั้งแอปพลิเคชัน
- **ไฟล์สำคัญในชั้นนี้:**
  - `CorsConfig.java` : ปลดล็อกให้ Frontend จากโดเมนอื่น (เช่น Vercel) สามารถยิง API ข้ามมาหา Backend (Render) ได้โดยไม่โดนบล็อก (แก้ปัญหา Cross-Origin Resource Sharing)
- **ทำไมต้องแยก:** เราไม่ควรเอาโค้ดตั้งค่าเซิร์ฟเวอร์หรือ Security ไปปนกับลอจิกของเกมใน Service หรือ Controller การแยกออกมาไว้ใน `config/` ทำให้เรารู้ได้ทันทีว่าถ้ามีปัญหาเรื่องการเชื่อมต่อเซิร์ฟเวอร์ ต้องมาหาที่โฟลเดอร์นี้ครับ

### 💡 บทสรุป: ทำไมถึงต้องเหนื่อยแบ่งเยอะขนาดนี้?
การแบ่งโฟลเดอร์แบบนี้คือการปฏิบัติตามหลักการ **Separation of Concerns (SoC)** และ **SOLID Principles** อย่างเคร่งครัด ซึ่งมีข้อดีคือ:
1. **ทำงานเป็นทีมได้ง่าย:** คนนึงทำ Controller อีกคนปั้นลอจิกใน Service โดยไฟล์ไม่ชน (Conflict) กัน
2. **แก้ไขง่าย (Maintainability):** ถ้าโครงสร้างตารางเปลี่ยน ก็โฟกัสแก้แค่ที่ `entity/` และ `repository/` โดยที่ `controller/` ไม่ได้รับผลกระทบ
3. **ทดสอบง่าย (Testability):** สามารถเขียน Unit Test เจาะจงไปที่ Service แต่ละไฟล์ได้เลย โดยจำลองการทำงาน (Mock) ของ Repository ได้ง่ายๆ (Dependency Injection)
