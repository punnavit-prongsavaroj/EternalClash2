# สรุปโครงสร้างโปรเจคและเหตุผลในการแบ่งโฟลเดอร์ (Layered Architecture)

โปรเจคนี้ถูกออกแบบตามสถาปัตยกรรม **Layered Architecture** ซึ่งเป็นการแบ่งซอร์สโค้ดออกเป็นชั้นๆ (Layers) โดยมีกฎเหล็กคือ "แต่ละชั้นจะมีหน้าที่เฉพาะของตัวเอง และห้ามเรียกข้ามชั้นกระโดดไปมา" (เช่น Controller ห้ามเรียกใช้ Repository โดยตรง ต้องผ่าน Service เสมอ)

การแบ่งโฟลเดอร์ใน `src/main/java/com/eternalclash2/` มีดังนี้:

## 1. 📁 `controller/` (Presentation Layer)
- **คืออะไร:** โฟลเดอร์สำหรับรับ Request จากผู้ใช้งาน (เช่น Frontend, Postman) และส่ง Response กลับไป โดยมักใช้คู่กับ Annotation `@RestController`
- **ทำไมต้องแยก:** เพื่อให้คลาสนี้ทำหน้าที่แค่ "รับ-ส่งข้อมูล" เท่านั้น (Single Responsibility) คลาสนี้ไม่ควรมีความรู้ว่าต้องคำนวณภาษียังไง หรือบันทึกฐานข้อมูลด้วยคำสั่งอะไร หน้าที่ของมันคือรับคำสั่งแล้วโยนต่อให้ Service ไปจัดการ

## 2. 📁 `service/` (Business Logic Layer)
- **คืออะไร:** หัวใจหลักของแอปพลิเคชัน เป็นที่เก็บลอจิกการคำนวณ กฎเกณฑ์ทางธุรกิจ (Business Rules) และการจัดการ Transaction (`@Transactional`)
- **ทำไมต้องแยก:** เพื่อรวมลอจิกซับซ้อนไว้ที่เดียว หากวันหน้า Frontend เปลี่ยนไป (เช่น เลิกใช้ React ไปใช้ Mobile App) โค้ดส่วน Service นี้จะยังใช้งานได้เหมือนเดิม 100% โดยไม่ต้องแก้ เพราะมันไม่ผูกติดกับหน้าจอ

## 3. 📁 `repository/` (Data Access Layer)
- **คืออะไร:** โฟลเดอร์สำหรับติดต่อกับฐานข้อมูล (Database) โดยตรง มักใช้ Spring Data JPA (`JpaRepository`)
- **ทำไมต้องแยก:** เพื่อซ่อนความซับซ้อนของการเขียน SQL หรือการต่อฐานข้อมูลเอาไว้ (Repository Pattern) ทำให้ Service ไม่ต้องสนใจว่าจะใช้ Database ค่ายไหน แค่สั่ง `save()` หรือ `findById()` ก็พอ

## 4. 📁 `domain/` (Domain Model Layer)
แบ่งย่อยเป็น:
- **`entity/`**: คลาสที่สะท้อนถึงตารางในฐานข้อมูล (เช่น `Game`, `Player`) ซึ่งผูกกับ JPA (`@Entity`)
- **`enums/`**: ค่าคงที่ต่างๆ ที่ใช้ในระบบ (เช่น `GameStatus`, `EventType`)
- **ทำไมต้องแยก:** เพื่อให้เห็นถึง "สิ่งที่มีอยู่จริง" ในโลกของระบบเกมนี้ เป็นแกนกลางที่ทุก Layer ต้องรู้จักและเรียกใช้ร่วมกัน

## 5. 📁 `dto/` (Data Transfer Object)
- **คืออะไร:** คลาสที่ใช้บรรจุข้อมูลสำหรับ "ส่งออก" หรือ "รับเข้า" จากภายนอก (API Contract)
- **ทำไมต้องแยก:** เพื่อป้องกันการส่ง `Entity` ออกไปโดยตรง ซึ่งอาจทำให้ข้อมูลความลับหลุดรอด (เช่น รหัสผ่าน) หรืออาจเกิดปัญหา Infinite Recursion เวลาแปลงเป็น JSON นอกจากนี้ยังช่วยให้เราปรับเปลี่ยนโครงสร้าง Database ได้โดยไม่กระทบกับ API ของ Frontend (DTO Pattern)

## 6. 📁 `mapper/`
- **คืออะไร:** คลาสที่ทำหน้าที่แปลงร่างข้อมูลไปมา ระหว่าง `Entity` กับ `DTO` 
- **ทำไมต้องแยก:** เพราะลอจิกการแปลง (Mapping) เช่น การนำชื่อ+นามสกุลมารวมกัน ควรแยกออกมาจาก Service เพื่อไม่ให้ Service บวม (Fat Service) และแยกออกจาก Entity เพื่อไม่ให้ Entity รู้จัก DTO

## 7. 📁 `exception/`
- **คืออะไร:** เก็บ Custom Exception ที่เราสร้างขึ้นเอง (เช่น `BusinessLogicException`) และ Global Exception Handler (`@RestControllerAdvice`)
- **ทำไมต้องแยก:** เพื่อรวมศูนย์การจัดการ Error และแปลง Error เหล่านั้นเป็น HTTP Status / JSON Format ที่มีมาตรฐานเดียวกันทั้งโปรเจค

## 8. 📁 `config/`
- **คืออะไร:** เก็บไฟล์ตั้งค่าของ Spring Boot (เช่น ตั้งค่า Security, CORS, Swagger/OpenAPI)
- **ทำไมต้องแยก:** เพื่อให้โค้ดส่วน Configuration แยกขาดจากส่วนการทำงาน (Logic) ทำให้ดูแลจัดการง่าย

## 9. 📁 `common/` หรือ `util/`
- **คืออะไร:** เครื่องมือ Utility ทั่วไปที่ไม่ได้ขึ้นกับ Business Logic (เช่น ตัวสุ่มข้อความ, ฟังก์ชันจัดการวันที่)

---

### 💡 บทสรุป: ทำไมถึงต้องเหนื่อยแบ่งเยอะขนาดนี้?
การแบ่งโฟลเดอร์แบบนี้คือการปฏิบัติตามหลักการ **Separation of Concerns (SoC)** และ **SOLID Principles** การแยกส่วนจะช่วยให้:
1. **ทำงานเป็นทีมได้ง่าย:** คนนึงทำ Frontend/Controller อีกคนทำลอจิก Service โดยไม่ตีกัน
2. **แก้ไขง่าย (Maintainability):** ถ้า Database เปลี่ยน ก็แก้แค่โฟลเดอร์ `repository/` และ `entity/` ส่วนอื่นไม่ต้องยุ่ง
3. **ทดสอบง่าย (Testability):** สามารถเขียน Unit Test เจาะจงไปที่ Service ได้เลย โดยสวมรอย (Mock) Repository ได้ง่ายๆ (Dependency Injection)
